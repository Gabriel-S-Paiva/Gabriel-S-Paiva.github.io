I turned a dusty school laptop into my server (and the network was the hard part)

A laptop bought for online school sat unused for four years. Now it runs my projects. This is how it got there, what broke along the way, and what's still missing.

homelabdockercaddyci-cdtailscalelinux

This is the story of the machine that runs my projects: this portfolio, my self-hosted cloud, and the CI that deploys them. It’s a story and not a tutorial, and everything identifying (addresses, hostnames, ports) is left out on purpose.

Where it came from

The laptop was an old Teclast. It had been bought for my brother’s online school, mostly for two reasons the school cared about: the screen size and the battery life. The hardware aged badly. It was outdated almost immediately, and then it spent about four years collecting dust.

When I wanted a place to host my own projects, it was sitting right there. I’ll be upfront: it is a weak machine. I didn’t pick it, it was just the one I had.

The hardware chose my software

I don’t have benchmarks, so I won’t pretend this is a performance story. The claim is about choices. With a machine like that, I picked tools that don’t ask for much:

  • Go for the backend, because it compiles to a small, fast binary.
  • SQLite instead of a database server, so there’s one less thing eating RAM.
  • Astro for the portfolio, so the site is static files served by a tiny web server.

Those were all software decisions. I didn’t tune the hardware or measure anything. I just stopped choosing things the machine couldn’t comfortably run.

Getting it online was the real project

The missing Ethernet port decided how setup began. Before I could SSH into the machine even once, I had to configure Wi-Fi from scratch in a way that would also reconnect after a restart. I was learning Linux at the same time, on a server that couldn’t reach the network until I’d gotten it right.

The fix for the last one was Tailscale. My dev machine and the server now sit on the same private network, and I connect over that, so SSH no longer depends on the router being in a good mood.

The lesson I took from this is that almost nothing that went wrong was about my code. It was networking, from start to finish.

What runs on it

Everything is a Docker Compose project. The portfolio is one, the cloud is another, and a small gateway sits in front of both and decides where traffic goes.

If you’re curious about why the cloud’s login works over plain HTTP on a home network, that’s the single-origin setup, which I explain in the Owned Cloud case study.

What this says about how I work

I treat infrastructure as part of the project, not as something someone else sets up. I got a machine from nothing to serving real projects, I debugged problems that had nothing to do with my own code, and I can tell you what’s broken, what’s missing and what comes next. I can’t promise it’s production-grade, but it’s honest.
