What it is

SAM (Sistema de Apoio Municipal) connects four groups: institutions that publish what they need, businesses that offer goods or services cheaply or for free, patrons who fund the system, and citizens who walk up to a touch panel in the street. An admin approves needs and matches them to offers. A citizen picks an item to donate, gets a 6-digit PIN by email and a printed receipt, then drops the item in a smart locker that checks the PIN and senses the door opening and closing.

It was the interdisciplinary WebPII project for 2025/26 and it won Best WebPII Project. It was a team of three, and this page covers the backend.

How a donation travels

Who built what

The repos are public and git blame is there for anyone who checks, so the split is stated up front.

Me (Backend). The relational schema and the UML, written up in the first semester. In the backend: the MVC structure, the Sequelize and Mongoose models, the CRUD controllers and endpoints, the REST API documentation, the error and validation layer, and the authentication and authorization system. Blame on the final backend puts about 54% of the surviving JavaScript lines on this author.

Teammate A. The whole Nuxt frontend, the Figma prototype, the deployment and the server it runs on, Socket.IO notifications, transactional email, rate limiting and helmet, the thermal printer, and the locker and panel hardware.

Teammate B. The Python data generator that produced the synthetic datasets, plus the exporters.

Two areas were shared and are marked where they appear: refresh-token reuse detection, and testing.

Two databases, and what it costs

MySQL, through Sequelize, is the source of truth: entities, needs, donations, leads and lockers. MongoDB, through Mongoose, holds what is high-volume or loosely shaped: telemetry, audit and interaction logs, notifications, vouchers, and the refresh and API tokens.

The two stores are only joined in the application. A Mongo document stores a SQL primary key, and that is the whole link. The trade-off is real: the database cannot enforce that the key exists, so the code has to. The models and the dual-connection setup live in db.config.js, with 26 Sequelize associations declared there. The hybrid design itself came out of the team’s first-semester analysis, so it is a team decision.

Authentication

Access tokens last 15 minutes and refresh tokens 7 days. Passwords use bcrypt. Every login creates a random token family id, and every refresh issues a new refresh token and revokes the old one. The stored token also records the IP address and user agent.

The point of the family is theft detection. If a refresh token that was already revoked shows up again, somebody is using a copy, so the whole family is revoked and the user has to log in again.

The rotation, the logout and the RefreshTokens model with its token family were written by the backend author. Teammate A later extended it so that reuse revokes the whole family, which is the updateMany branch above.

Authorization is three small middleware functions. verifyJWT accepts a JWT or a permanent API token with a sam_ prefix, stored only as a hash. requireRoles checks the role against a list. adminOrSelf lets a request through if the caller is an admin or the entity named in the URL, and rejects any identifier that is not exactly nine digits. The API tokens and a service-to-service shortcut were added by Teammate A.

One error shape for the whole API

Every failure goes through next(err) into a single error handler, and every error carries a status and an errors map. The frontend can then show field-level messages without parsing strings.

The shape is not fully consistent: errors is a map in some helpers and an array of single-key objects in others, a leftover from writing them over several weeks. One shape would be better.

Transactions where it matters

Creating a lead can create a citizen too, and a lead must never exist for an item that is already taken. That is several writes and several checks, so it runs inside a Sequelize transaction with an explicit rollback on every early exit.

Two weaknesses on a second read. The PIN is passed in by the client in pin_entrega, not generated by the server, which is the wrong side of the trust boundary. And the early rollback() calls mean the catch block can try to roll back a transaction that is already closed.

Testing: what the numbers say

The report split testing by ISTQB roles. Teammate A was Test Manager with Jira and Xray, Teammate B was Test Analyst, and the backend author was assigned Performance Test Engineer. The JMeter scripts in the tests repo were written by Teammate A, so the results below are reported without claiming their authorship.

The most useful finding is where the slowness was. JMeter hit the frontend, and the latency target was missed badly. The API reads underneath were fast: the needs list took 308 ms, donations 276 ms, leads 165 ms. The report’s own recommendation was caching or a CDN in front of the frontend, and a health-check endpoint, which the API does not have.

The backend repo has no tests of its own. Its test script is the default stub. Everything above lives in a separate repo and hits the deployed system. The backend author contributed early scaffolding to that repo, but little of it survives.

Where it stands

What should change

  • Freeze the API contract before the frontend builds against it. One existed in Notion and still drifted.
  • Write backend tests in the backend repo, alongside the features and not at the end.
  • Generate the PIN on the server.
  • Scope machine-to-machine access narrowly, and authenticate every route by default.
  • Persist locker state and add a health endpoint.
