Owned Cloud

A self-hosted family cloud drive running on my own home server. I built the Go backend and the SvelteKit frontend alone, as a way to learn a new stack by shipping something real.

What it is

Owned Cloud is a private file drive for a family: folders, sharing with view or edit permissions, and a storage quota per person. It runs on a laptop in my home, so nobody else’s server ever holds the files.

I started it because I had old hardware that was too slow to be a main machine and too good to throw away, and because I wanted to learn Go and SvelteKit by building something I would actually use. I come from Node, Express and Vue. I designed the schema, API, auth, frontend and deployment myself, then spent the second half of the project treating it like production software: tests, CI, a security policy.

Why Go, and what I did differently from Express

I built the Go backend on purpose without a framework. My DEVLOG has the moments where the model changed for me: Go middleware is a function that takes a handler and returns a handler, not a next() callback. A nullable foreign key is a sql.NullInt64, not a value you can scan into an int. A slice is a pointer, a length and a capacity, so slicing one does not copy it.

The backend has three layers and one rule: HTTP handlers call the storage layer, and only the storage layer writes SQL. The router lives in its own file (router.go) so tests can build the whole app without starting a server.

How it runs

The server is a repurposed Teclast F15S laptop (Celeron N4020, 6 GB of RAM, 128 GB of storage, Wi-Fi only) running Ubuntu Server. That shaped decisions early: a small compiled binary instead of a heavy runtime, SQLite instead of a database server, and builds I try not to run twice.

The part I would defend in an interview is the single origin. The frontend and the API are served from the same address, with Caddy stripping the /api prefix before it reaches Go. Because of that, the session cookie can stay HttpOnly without SameSite=None; Secure, which would need HTTPS. On a LAN over plain HTTP, that is the difference between a secure cookie and no login at all. I did not start with that idea. It came from not having a domain or TLS yet.

Decisions in the backend

Sessions, not JWT

JWT was my default. Then I looked at what it buys you: no database lookup per request. For about five users on a local machine, that lookup costs nothing, and the moment you add refresh tokens you are checking the database anyway. So I used server-side sessions: a random token from crypto/rand, stored in a Sessions table and sent in an HttpOnly cookie. They are also trivial to revoke. Passwords are hashed with bcrypt. JWT is on the roadmap for a future mobile client, where it would actually earn its place.

Approval before access

Sign-up does not create an account. It creates a row in Requests, and an admin approves it. Approval is one transaction, and it is also where each user gets their root folder.

I gave every user an explicit root folder row instead of treating “no parent” as the root. A null-parent root means every folder query needs a special case for it. A real row means a folder is a folder. It came out of a frontend conflict, not a plan: I had to change user creation after the first version.

Sharing that the database enforces

A share points at either a file or a folder, never both and never neither. I put that rule in the schema, so a bug in a handler cannot create a half-valid share.

The access query joins Shares and returns the caller’s permission as Owner, View or Edit. That is why the code has FileAccess and not just FileOwnership: someone with Edit permission can act on a file without being treated as its owner.

Uploads in two phases, with the quota reserved up front

Uploading is split in two. First the client announces the file (name, size, type). The server checks the quota and records the file as Uploading in one transaction. Then the client sends the bytes, and the server appends them to a file on disk.

I also added a sliding-window rate limiter as middleware: five requests per minute per client on login and on sign-up. It keys on the first X-Forwarded-For address, because behind two Caddy layers the socket address is always a proxy.

Treating a side project like production

The first version worked, and I stopped adding features. Version 1.0.0 is the result of a review pass over the whole backend, then tests, then automation.

  • Tests. Storage-layer tests for the stores, integration tests that call the real router through httptest, tests for the rate limiter, and Vitest tests across the frontend stores and api.ts.
  • CI. On every pull request: go vet, golangci-lint, govulncheck, build and test for the backend; lint, type check, tests and build for the frontend. A frontend dependency audit runs too, but it does not block.
  • Deploy. A merge to main triggers a job on a self-hosted runner inside my network. It pulls, rebuilds and restarts the containers on the home server. The server never needs to be reachable from the internet for that to work.
  • Workflow. Protected main, pull requests from branches, Husky pre-commit hooks so formatting failures never reach CI, and Dependabot for Go, npm, Docker and Actions.
  • Project files. SECURITY.md with GitHub private vulnerability reporting, CONTRIBUTING.md, a code of conduct, and issue and pull request templates.

The frontend

I designed the interface like a vault ledger: moss green, brass, rust and a sage-white page, with Fraunces for headings, Public Sans for text and JetBrains Mono for numbers. The fonts are self-hosted so the app makes no third-party requests. Tailwind v4 is wired to plain CSS variables through @theme inline, so the palette is defined once and reused as utilities.

There is one FileItem and one FolderItem component with list and grid variants, drag and drop to move things between folders (native HTML5 events), and Svelte 5 rune stores for the drive, navigation, shared items, auth and toasts.

I learned the frontend in three phases on purpose, because I was learning Svelte at the same time: raw HTML first so the features worked, then the code organised into components, then Tailwind last. Doing all three at once is how you get a rewrite.
